# troubleshooting-playbook

修东西卡住时，先查、再动手。验收标准是真实端到端数据面测试，不是表面信号。

## 规则

1. 验收 = 真实端到端数据面测试。面板 200、订阅已下发、WS 101 握手正确都通过了，节点仍可能零流量——用真实协议客户端测一遍再交给 Luca，不让他当测试 harness。
2. 出故障先在日志里定位断点：请求到底有没有到达。日志里在测试窗口内什么都没有，断点就在 Xray 上游，所有 Xray 内部理论（进程死、DNS）都是白费动作；基于未验证猜测的修复不许上。报「东西不见了」前先查删除记录/是谁删的——Luca 自己删的要先认出来，不要当 bug 修；已删无恢复路径时走重新上架，不重生成。
3. 同一故障跨两个部署/配置出现，怀疑架构/链路，不怀疑配置。
4. 手修之前先调研：平台官方模板/市场 → kit 的 GitHub issues/README → 社区（X / 论坛）。一轮搜索胜过一上午猜。
5. 身份碎片：同一服务不同登录方式（邮箱验证码 vs GitHub OAuth）可能是分开的账号、分开的工作区——先核实落到了哪个工作区再承诺。Cloady：Gmail 账号持有 WORKSPACE-XS6CS0，GitHub 登录开了个空的 "Aoki" 账号；站规：Cloady 控制台只走 GitHub。
6. 一次任务只用一个连续浏览器会话；登录态靠已持久的会话，不反复重登。

## 验收

- 修复汇报写明：端到端实测方法 + 结果；日志定位到的断点；架构还是配置的判断及依据；查过的官方模板/issues/社区来源。
- 缺实测结果的「修好了」不报。
